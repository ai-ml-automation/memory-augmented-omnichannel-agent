# 🏛️ ARCHITECTURE_DECISIONS.md

## 1. Введение

### 1.1. Цель документа

Данный документ содержит детальное описание всех ключевых архитектурных решений, принятых при разработке системы «Омниканальный агент с долговременной памятью». В отличие от [ARCHITECTURE.md](ARCHITECTURE.md), где представлен общий обзор архитектуры, настоящий документ фокусируется на **обосновании каждого решения**, анализе альтернатив, компромиссах и конкретной реализации в коде.

Каждое решение документировано по следующему шаблону:

- **Контекст** — в каких условиях принималось решение.
- **Альтернативы** — какие другие подходы рассматривались.
- **Обоснование** — почему выбран именно этот подход.
- **Компромиссы** — какие недостатки или ограничения существуют.
- **Реализация** — конкретные файлы, классы, методы, примеры кода.
- **Связанные решения** — ссылки на другие ADR.

Документ предназначен для архитекторов, разработчиков, технических лидов и всех, кто хочет понять, почему система устроена именно так, а не иначе.

### 1.2. Принципы принятия решений

Все архитектурные решения руководствуются следующими принципами (зафиксированы в [ARCHITECTURE.md](ARCHITECTURE.md), раздел 2):

1. **KISS** — минимум сложности, только необходимая функциональность.
2. **YAGNI** — никакого кода «на будущее».
3. **Production-first** — сразу используем реальные БД, очереди, кэш.
4. **Parallel Frontend** — API-контракты определяются на старте.
5. **Минимум тестов** — только E2E, интеграционные и критичные unit-тесты.
6. **Никаких отложенных фич** — всё из SPEC реализовано в текущем релизе.
7. **РФ-специфика** — полное соответствие 152-ФЗ, приоритет российских облаков.
8. **Feature Flags** — тяжёлые сервисы управляются флагами.
9. **Lazy Initialization** — модели загружаются при первом вызове.
10. **Монолит на первом этапе** — всё в одном FastAPI приложении.

## 2. Решение #1: На первом этапе монолит вместо микросервисов

### 2.1. Контекст

Система включает множество компонентов: API-шлюз, агенты (LangGraph), слой памяти (PostgreSQL, Qdrant, Neo4j, Redis), внешние интеграции (мессенджеры, телефония, LLM, ASR, TTS), фоновые задачи (Celery), мониторинг. Вопрос: разбивать ли на микросервисы или делать монолит.

### 2.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Микросервисы** | Каждый компонент (API, агенты, обработка голоса, работа с памятью) выделен в отдельный сервис с собственным REST/gRPC API. |
| **Модульный монолит** | Одно приложение с чёткими модулями, которые могут быть вынесены позже. |
| **Serverless** | Функции AWS Lambda / Yandex Cloud Functions для каждого эндпоинта. |
| **Monolith (на первом этапе, выбран)** | Единое FastAPI приложение, развёртываемое как один pod. |

### 2.3. Обоснование

**Причины выбора монолита на первом этапе:**

1. **Простота разработки и отладки** — нет распределённых транзакций, нет сетевых задержек между компонентами, единый стек (Python).
2. **Скорость итераций** — изменение одного модуля не требует пересборки и передеплоя десятков сервисов.
3. **Единая кодовая база** — проще поддерживать согласованность версий, обновлять зависимости, управлять конфигурацией.
4. **Начальный этап** — система на стадии пилота, количество пользователей ограничено. Монолит проще масштабировать горизонтально при необходимости (K8s HPA).
5. **LangGraph и Celery** — оркестрация агентов и асинхронные задачи хорошо работают внутри одного приложения, не требуя межсервисного взаимодействия.

**Компромиссы:**

- На первом этапе масштабирование только всего приложения целиком (нельзя отдельно масштабировать только агенты или только API).
- Ошибка в одном модуле может уронить всё приложение (нивелируется через health‑checks и graceful degradation).
- Сложность внедрения разных языков/технологий (не планируем).

### 2.4. Реализация

**Файл:** [backend/src/main.py](../backend/src/main.py)

Приложение создаётся единой точкой входа. Все роутеры подключаются в одном месте:

```python
# backend/src/main.py
app = FastAPI(...)

app.include_router(health_router)
app.include_router(auth_router)
app.include_router(consents_router)
app.include_router(webhooks_router)
app.include_router(admin_users_router)
app.include_router(admin_channels_router)
app.include_router(memory_router)
app.include_router(chat_router)
app.include_router(voice_router)
app.include_router(analytics_router)
```

**Горизонтальное масштабирование:** Приложение разворачивается в Kubernetes с HPA, что позволяет увеличивать число реплик при росте нагрузки. В [k8s/base/hpa.yml](../k8s/base/hpa.yml) настроен автомасштабирование от 2 до 10 подов по CPU и Memory.

**Связанные решения:** ADR #7 (HPA) в [ARCHITECTURE.md](ARCHITECTURE.md).

## 3. Решение #2: LangGraph для оркестрации агентов

### 3.1. Контекст

Система использует нескольких AI-агентов: извлечение фактов, управление памятью, генерация ответов, разрешение конфликтов, фоновое устаревание. Требуется фреймворк для построения детерминированных, управляемых графов с поддержкой чекпоинтов и human-in-the-loop.

### 3.2. Альтернативы

| Инструмент | Описание |
|------------|----------|
| **CrewAI** | Ролевая модель агентов, последовательные вызовы, меньше контроля. |
| **AutoGen** | От Microsoft, многоагентные диалоги, но менее детерминирован. |
| **LangChain Agents** | Более простые агенты, без строгих графов состояний. |
| **Кастомная реализация** | Написать свою оркестрацию на основе asyncio. |
| **LangGraph (выбран)** | Фреймворк от LangChain для построения графов состояний с условными переходами, чекпоинтами, HITL. |

### 3.3. Обоснование

**Причины выбора LangGraph:**

1. **Детерминизм** — строгий граф состояний, предсказуемый поток, что важно для юридической прозрачности (действия агента должны быть объяснимы).
2. **Чекпоинты** — возможность сохранять состояние агента между вызовами (в Redis), что позволяет восстанавливать сессии при сбоях.
3. **Human-in-the-Loop (HITL)** — встроенная поддержка паузы для ручного утверждения критичных действий (например, удаление памяти).
4. **Условные переходы** — возможность ветвления логики в зависимости от состояния (например, если конфликт требует вмешательства оператора).
5. **Интеграция с LangChain** — легко использовать готовые инструменты и промпты.
6. **Производственная зрелость** — используется в крупных проектах, активное сообщество.

**Компромиссы:**

- Дополнительная сложность по сравнению с простыми агентами.
- Зависимость от экосистемы LangChain (но мы уже используем её компоненты).

### 3.4. Реализация

**Директория:** [backend/src/agents/](../backend/src/agents/)

Все агенты наследуют или используют LangGraph. Каждый агент — это отдельный граф или подграф, который может быть вызван из основного пайплайна.

**Пример: FactExtractorAgent** ([backend/src/agents/fact_extractor.py](../backend/src/agents/fact_extractor.py))

```python
# Упрощённая структура
class FactExtractorAgent:
    async def extract(self, message: str) -> list[dict]:
        # Шаг 1: LLM-извлечение
        facts = await self._extract_triplets(message)
        # Шаг 2: Фильтрация эмоций
        facts = self._filter_emotions(facts)
        # Шаг 3: Анонимизация PII
        facts = self._anonymize_pii(facts)
        return facts
```

Хотя здесь не используется полноценный граф, архитектура позволяет легко заменить на `StateGraph` в будущем. Для более сложных агентов (например, `ResponseGenerator`) используется граф с несколькими узлами.

**Чекпоинты:** LangGraph поддерживает сохранение состояния в Redis через `RedisSaver`. В проекте это используется для сохранения контекста сессии.

**Связанные решения:** ADR #1 в [ARCHITECTURE.md](ARCHITECTURE.md).

## 4. Решение #3: Mem0 как Memory Layer

### 4.1. Контекст

Необходим специализированный слой для управления памятью агента: хранение фактов, векторный поиск, графовые связи, устаревание (decay), разрешение конфликтов. Существуют готовые решения, либо можно реализовать кастомный слой поверх Qdrant/Neo4j.

### 4.2. Альтернативы

| Инструмент | Описание |
|------------|----------|
| **Mem0** | Специализированный open‑source слой памяти с интеграцией с LangGraph, поддержкой Qdrant, Neo4j, decay, конфликтов. |
| **Zep** | Альтернативный слой памяти с временными графами, менее активное сообщество. |
| **LangChain Memory** | Базовая память (ConversationBufferMemory, ConversationSummaryMemory), без векторного и графового поиска. |
| **Кастомная реализация** | Написать свой слой поверх SQLAlchemy, Qdrant, Neo4j. |
| **Mem0 (выбран)** | Готовое решение с активной экосистемой и интеграцией с LangGraph. |

### 4.3. Обоснование

**Причины выбора Mem0:**

1. **Интеграция с LangGraph** — нативная поддержка через LangChain, что упрощает использование в агентах.
2. **Графовая память** — поддержка хранения связей между фактами (через Neo4j), что необходимо для сложных запросов (причинно-следственные связи).
3. **Memory Decay** — встроенный механизм устаревания фактов по времени (вес уменьшается, факты удаляются).
4. **Разрешение конфликтов** — встроенная логика разрешения противоречий между фактами из разных каналов.
5. **Активное сообщество** — регулярные обновления, документация, примеры.
6. **Модульность** — можно подменять бэкенды (Qdrant → Pinecone, Neo4j → Amazon Neptune).

**Компромиссы:**

- Ограниченное горизонтальное масштабирование (один инстанс Mem0). Для пилота этого достаточно, в будущем планируется обёртка с балансировкой (см. ADR #8).
- Дополнительная зависимость от внешнего open‑source проекта.

### 4.4. Реализация

**Файлы:**
- [backend/src/services/memory_service.py](../backend/src/services/memory_service.py) — абстрактный интерфейс.
- [backend/src/services/mem0_memory_service.py](../backend/src/services/mem0_memory_service.py) — конкретная реализация с Mem0.

**Ключевой паттерн:** абстракция позволяет в будущем заменить Mem0 на Zep или кастомную реализацию без изменения агентов.

```python
# backend/src/services/mem0_memory_service.py
class Mem0MemoryService(MemoryService):
    async def store_fact(self, user_id, fact_type, value, channel, weight):
        # 1. Сохраняем в PostgreSQL (через FactService)
        fact = await self._fact_service.store_fact(...)
        # 2. Индексируем в Qdrant (best-effort)
        await self._vector_store.index_fact(...)
        # 3. Создаём узел в Neo4j (best-effort)
        await self._graph_service.create_fact_node(...)
        return fact
```

**Связанные решения:** ADR #2, ADR #8 в [ARCHITECTURE.md](ARCHITECTURE.md).

## 5. Решение #4: Qdrant + Neo4j для хранения фактов

### 5.1. Контекст

Факты памяти должны поддерживать два типа поиска: семантический (по смыслу) и структурный (по связям). Одна база данных не может эффективно обеспечить оба подхода одновременно.

### 5.2. Альтернативы

| Инструмент | Описание |
|------------|----------|
| **Только Qdrant** | Векторная БД, хорош для семантического поиска, но слаб для графовых запросов (нет связей). |
| **Только Neo4j** | Графовая БД, хорош для связей, но плох для семантического поиска (нет векторов). |
| **Pinecone + Neptune** | Облачные аналоги Qdrant и Neo4j, но дороже и требуют выхода в интернет. |
| **Weaviate** | Векторная БД с поддержкой графов, но менее зрелая и слабее Neo4j для сложных запросов. |
| **Qdrant + Neo4j (выбран)** | Комбинированное решение: Qdrant — для семантического поиска, Neo4j — для графовых запросов. |

### 5.3. Обоснование

**Причины выбора комбинации:**

1. **Qdrant** — быстрый семантический поиск по эмбеддингам, горизонтально масштабируется, имеет кластеризацию (Raft).
2. **Neo4j** — мощный графовый движок с Cypher, позволяет выполнять сложные запросы типа «какие тарифы интересовали клиента за последний месяц».
3. **Разделение ответственности** — каждая БД решает свою задачу, не перегружая другую.
4. **Согласованность** — синхронизация на уровне `MemoryManager`, eventual consistency допустима для памяти.
5. **On‑premise готовность** — оба продукта можно развернуть локально без облачных зависимостей.

**Компромиссы:**

- Дублирование данных (факты хранятся в двух БД) → требуется синхронизация.
- Дополнительные накладные расходы на поддержку двух БД.
- Возможная рассинхронизация при сбоях (но это решается graceful degradation).

### 5.4. Реализация

**Qdrant:** [backend/src/services/vector_store_service.py](../backend/src/services/vector_store_service.py)

- Эмбеддинги: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (384 dim).
- Методы: `index_fact()`, `search_similar()`, `delete_fact()`.

**Neo4j:** [backend/src/services/graph_service.py](../backend/src/services/graph_service.py)

- Асинхронный драйвер (`AsyncGraphDatabase`).
- Методы: `create_fact_node()`, `create_relationship()`, `get_user_facts_graph()`, `delete_fact_node()`.

**Синхронизация:** выполняется в `Mem0MemoryService` через вызовы обоих сервисов с обработкой ошибок (graceful degradation — если один сервис недоступен, работа продолжается с другим).

## 6. Решение #5: Celery для асинхронных задач

### 6.1. Контекст

Извлечение фактов (вызов LLM) и фоновое устаревание (decay) могут занимать несколько секунд. Эти операции не должны блокировать ответ пользователю. Требуется очередь задач.

### 6.2. Альтернативы

| Инструмент | Описание |
|------------|----------|
| **Celery** | Зрелая распределённая очередь задач с поддержкой Redis, RabbitMQ, Beat (планировщик). |
| **Dramatiq** | Более лёгкая альтернатива Celery, но без встроенного Beat. |
| **ARQ** | Асинхронная очередь на основе Redis, простая, но мало мониторинга. |
| **Redis Streams напрямую** | Использовать Redis Streams для очередей и вручную реализовать воркеры. |
| **Celery (выбран)** | Стандарт де‑факто в Python, зрелый, богатый мониторинг. |

### 6.3. Обоснование

**Причины выбора Celery:**

1. **Зрелость** — используется более 15 лет, множество production-проектов.
2. **Beat** — встроенный планировщик для периодических задач (DecayAgent).
3. **Мониторинг** — Flower, Prometheus exporter, интеграция с нашим стеком мониторинга.
4. **Поддержка Redis** — мы уже используем Redis как брокер, не нужно поднимать RabbitMQ.
5. **Простота** — конфигурация через `celery_app.py` и декораторы задач.

**Компромиссы:**

- Celery не поддерживает async/await напрямую (требуется адаптация через `asyncio.run()` внутри задач).
- Дополнительные процессы (воркеры) требуют управления (K8s Deployment).
- Сложность отладки распределённых задач.

### 6.4. Реализация

**Файлы:**
- [backend/src/celery_app.py](../backend/src/celery_app.py) — конфигурация приложения.
- [backend/src/tasks/message_tasks.py](../backend/src/tasks/message_tasks.py) — `process_message`.
- [backend/src/tasks/fact_tasks.py](../backend/src/tasks/fact_tasks.py) — `extract_facts`.
- [backend/src/tasks/decay_tasks.py](../backend/src/tasks/decay_tasks.py) — `run_decay_agent`.

**Beat schedule** (в `celery_app.py`):
```python
beat_schedule = {
    "decay-agent-hourly": {
        "task": "backend.src.tasks.decay_tasks.run_decay_agent",
        "schedule": 3600.0,  # раз в час
    },
}
```

**Запуск в Docker Compose:**
```yaml
celery-worker:
  command: celery -A backend.src.celery_app worker --loglevel=info --concurrency=4
celery-beat:
  command: celery -A backend.src.celery_app beat --loglevel=info
```

**Связанные решения:** ADR #5 в [ARCHITECTURE.md](ARCHITECTURE.md).

## 7. Решение #6: Async везде (SQLAlchemy, Neo4j, HTTP)

### 7.1. Контекст

FastAPI построен на asyncio. Все операции ввода-вывода должны быть неблокирующими, чтобы не замедлять обработку запросов.

### 7.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Синхронные драйверы** | Использовать синхронные версии (psycopg2, neo4j синхронный). |
| **Асинхронные драйверы (выбран)** | Использовать async-совместимые драйверы: asyncpg, AsyncGraphDatabase, httpx.AsyncClient. |
| **Пул потоков** | Использовать синхронные драйверы в отдельном пуле потоков (через `run_in_executor`). |

### 7.3. Обоснование

**Причины выбора асинхронных драйверов:**

1. **Производительность** — не блокирует event loop, позволяет обрабатывать тысячи одновременных соединений.
2. **Интеграция с FastAPI** — async/await — родной стиль, меньше синтаксического шума.
3. **Экосистема** — SQLAlchemy 2.0 поддерживает async, Neo4j 5.x имеет AsyncGraphDatabase.
4. **Масштабируемость** — при горизонтальном масштабировании async-приложения лучше утилизируют ресурсы.

**Компромиссы:**

- Некоторые библиотеки (например, neo4j асинхронный) менее стабильны, чем синхронные аналоги (но в проекте это решено тщательным тестированием).
- Async-код сложнее в отладке (стек вызовов менее очевиден).

### 7.4. Реализация

**SQLAlchemy async:** [backend/src/database.py](../backend/src/database.py)
```python
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession

engine = create_async_engine(settings.postgres_url, echo=False)
async_session_factory = async_sessionmaker(engine, class_=AsyncSession)
```

**Neo4j async:** [backend/src/services/graph_service.py](../backend/src/services/graph_service.py)
```python
from neo4j import AsyncGraphDatabase

driver = AsyncGraphDatabase.driver(settings.NEO4J_URI, auth=(...))
async with driver.session() as session:
    await session.run("MATCH (n) RETURN n")
```

**HTTP async:** Используется `httpx.AsyncClient` везде, где нужны внешние HTTP-запросы (LLM, health-проверки).

## 8. Решение #7: Feature Flags для тяжёлых сервисов

### 8.1. Контекст

Система зависит от внешних тяжёлых сервисов: LLM, ASR, TTS, Mem0. Эти сервисы могут быть недоступны, дороги или не нужны на ранних этапах. Требуется механизм их отключения.

### 8.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Условная компиляция** | Использовать `#ifdef`-подобные директивы (не в Python). |
| **Отдельные репозитории / ветки** | Держать код для разных конфигураций в разных ветках. |
| **Переменные окружения (Feature Flags)** | Простые флаги в `.env`, проверяемые в коде. |
| **Централизованное хранилище флагов** | Использовать LaunchDarkly или аналоги. |
| **Feature Flags (выбран)** | Простые флаги в `.env` с проверкой в коде. |

### 8.3. Обоснование

**Причины выбора переменных окружения:**

1. **Простота** — легко добавить новый флаг, проверить в коде.
2. **Лёгкость включения/выключения** — достаточно изменить `.env` и перезапустить приложение.
3. **Дешевизна** — не требует внешнего сервиса (LaunchDarkly).
4. **Отказоустойчивость** — если сервис недоступен, флаг позволяет переключиться на fallback.
5. **Прозрачность** — флаги видны в конфигурации, легко документируются.

**Компромиссы:**

- Требуется перезапуск приложения для изменения флагов (в отличие от динамических систем).
- Нет централизованного управления флагами (но для нашего масштаба это не критично).

### 8.4. Реализация

**Флаги в [backend/src/config.py](../backend/src/config.py):**
```python
class Settings(BaseSettings):
    ENABLE_LLM: bool = False
    ENABLE_VOICE: bool = False
    ENABLE_ASR: bool = False
    ENABLE_TTS: bool = False
    ENABLE_MEMORY: bool = False
```

**Использование в коде:**
```python
# backend/src/api/voice.py
if not settings.ENABLE_VOICE:
    raise HTTPException(503, "Voice disabled")
```

```python
# backend/src/main.py
if settings.ENABLE_VOICE:
    app.include_router(voice_router)
```

**Graceful degradation:** Если флаг выключен, соответствующие роуты не регистрируются, а попытка вызова возвращает ошибку 503 с понятным сообщением.

## 9. Решение #8: Lazy Initialization для ML-моделей

### 9.1. Контекст

Система использует ресурсоёмкие ML-модели: Whisper (ASR), Silero (TTS), Cross-Encoder (реранкинг), Sentence-Transformer (эмбеддинги). Загрузка всех этих моделей при старте приложения значительно увеличила бы время запуска и потребление памяти, даже если функции не используются.

### 9.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Загрузка при старте** | Все модели загружаются в `__init__` или на старте приложения. |
| **Ленивая загрузка (выбран)** | Модель загружается только при первом вызове соответствующего метода. |
| **Отдельные микросервисы для ML** | Модели вынесены в отдельные сервисы (как альтернатива, но противоречит монолиту). |
| **Кэширование моделей на диске** | Модели загружаются из кэша при первом обращении. |

### 9.3. Обоснование

**Причины выбора ленивой загрузки:**

1. **Быстрое время старта** — приложение запускается за секунды, а не минуты.
2. **Экономия памяти** — модели загружаются только если они действительно нужны (например, если Voice отключён — Whisper и Silero не загружаются).
3. **Гибкость** — модель может быть перезагружена без перезапуска всего приложения (например, при обновлении версии).
4. **Соответствие Feature Flags** — если флаг выключен, модель не загружается вообще.

**Компромиссы:**

- Первый запрос к модели может быть медленным (5–15 секунд для загрузки). Это решается предзагрузкой для критичных моделей (Cross-Encoder предзагружается при старте, если `ENABLE_LLM=true`).
- Сложность управления памятью при выгрузке моделей (пока не реализовано).

### 9.4. Реализация

**Пример: WhisperASR** ([backend/src/services/whisper_asr.py](../backend/src/services/whisper_asr.py))

```python
class WhisperASR:
    def __init__(self, model_name: str = "large-v3"):
        self.model_name = model_name
        self._model = None   # модель не загружена

    def _load_model(self):
        if self._model is None:
            import whisper
            self._model = whisper.load_model(self.model_name)
        return self._model

    async def transcribe(self, audio_data: bytes):
        model = self._load_model()   # загрузка только здесь
        # ...
```

**Аналогично для:** SileroTTS ([backend/src/services/silero_tts.py](../backend/src/services/silero_tts.py)), Cross-Encoder ([backend/src/services/memory_search_service.py](../backend/src/services/memory_search_service.py)).

**Предзагрузка Cross-Encoder:** в [backend/src/main.py](../backend/src/main.py) при старте (если `ENABLE_LLM=true`) запускается фоновая задача загрузки модели, чтобы первый запрос пользователя не ждал 15 секунд.

## 10. Решение #9: Circuit Breaker и Retry

### 10.1. Контекст

Система зависит от внешних сервисов (LLM, Qdrant, Neo4j). При их временной недоступности система должна не падать, а пробовать повторить запрос или переключиться на fallback.

### 10.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Бесконечные попытки** | Повторять запрос до успеха (может привести к зависанию). |
| **Быстрое падение** | При первой ошибке возвращать 500 (плохо для пользователя). |
| **Retry с ограничением** | Повторять запрос несколько раз с экспоненциальной задержкой. |
| **Circuit Breaker** | После нескольких ошибок перестать вызывать сервис на некоторое время. |
| **Retry + Circuit Breaker (выбран)** | Комбинация: retry для временных сбоев, circuit breaker для длительных. |

### 10.3. Обоснование

**Причины выбора комбинации:**

1. **Retry** — спасает от временных сетевых проблем, высокой нагрузки, таймаутов.
2. **Circuit Breaker** — предотвращает каскадный отказ, когда сервис долго не отвечает (экономит ресурсы).
3. **Отказоустойчивость** — система продолжает работать даже при сбоях внешних зависимостей (graceful degradation).
4. **Простота реализации** — библиотеки `tenacity` и `circuitbreaker` легко интегрируются.

**Компромиссы:**

- Увеличение времени ответа при повторных попытках.
- Сложность настройки порогов (сколько попыток, какой таймаут).

### 10.4. Реализация

**Планируемые файлы:** [backend/src/utils/resilience.py](../backend/src/utils/resilience.py)

```python
from tenacity import retry, stop_after_attempt, wait_exponential
import circuitbreaker

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, max=10))
async def call_llm_with_retry(prompt):
    return await llm.generate(prompt)

@circuitbreaker(failure_threshold=5, recovery_timeout=60)
async def call_qdrant_with_circuit(query):
    return await qdrant.search(query)
```

**Применение в коде:**
- `LLMService.generate` обёрнута в `@retry`.
- `VectorStoreService.search_similar` обёрнута в `@circuitbreaker`.
- `GraphService.create_fact_node` обёрнута в `@retry` с логированием.

**Связанные решения:** ADR #9 в [ARCHITECTURE.md](ARCHITECTURE.md).

## 11. Решение #10: Версионирование API (`/api/v1`)

### 11.1. Контекст

API системы будет развиваться: добавляться новые эндпоинты, меняться форматы ответов. Чтобы не ломать клиентов (фронтенд, внешние интеграции), требуется механизм версионирования.

### 11.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Без версионирования** | Все изменения вносятся напрямую, клиенты обновляются синхронно. |
| **Версионирование в URL** | `/api/v1/...`, `/api/v2/...` (выбран). |
| **Версионирование в заголовках** | `Accept: application/vnd.myapp.v1+json`. |
| **Согласование версий через query-параметр** | `?version=1`. |

### 11.3. Обоснование

**Причины выбора версионирования в URL:**

1. **Простота** — клиент явно указывает версию в каждом запросе.
2. **Читаемость** — легко понять, какая версия используется.
3. **Кеширование** — разные версии могут кешироваться отдельно.
4. **Обратная совместимость** — можно поддерживать несколько версий одновременно.

**Компромиссы:**

- Некоторое дублирование кода для разных версий (но мы планируем делать только мажорные изменения).
- Требуется планирование жизненного цикла версий.

### 11.4. Реализация

**Планируется в [backend/src/main.py](../backend/src/main.py):**

```python
app.include_router(auth_router, prefix="/api/v1")
app.include_router(consents_router, prefix="/api/v1")
# ... все роутеры с префиксом /api/v1
```

Фронтенд будет обновлён: `baseURL` в [frontend/src/api/axios.ts](../frontend/src/api/axios.ts) изменится на `http://localhost:8000/api/v1`.

## 12. Решение #11: Аутентификация через JWT в httpOnly cookie

### 12.1. Контекст

Требуется безопасная аутентификация пользователей с защитой от XSS и CSRF.

### 12.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Bearer token (JWT в заголовке)** | Клиент хранит токен в localStorage и передаёт в `Authorization`. |
| **JWT в httpOnly cookie (выбран)** | Токен хранится в cookie с флагом httpOnly, автоматически отправляется с запросами. |
| **Session-based (серверная сессия)** | Хранить сессии в Redis, передавать session_id в cookie. |

### 12.3. Обоснование

**Причины выбора httpOnly cookie:**

1. **Защита от XSS** — httpOnly cookie недоступна для JavaScript, украсть токен через XSS невозможно.
2. **Автоматическая отправка** — браузер сам отправляет cookie с каждым запросом, не нужно вручную добавлять заголовок.
3. **Простота** — не нужно хранить токен на клиенте, управлять обновлением.
4. **Поддержка CSRF** — можно комбинировать с double‑submit cookie.

**Компромиссы:**

- Уязвимость к CSRF (решается double‑submit cookie).
- Cookie не работает для мобильных приложений без поддержки cookie (но мы планируем только веб).

### 12.4. Реализация

**Установка cookie:** [backend/src/api/auth.py](../backend/src/api/auth.py)

```python
response.set_cookie(
    key="access_token",
    value=token,
    httponly=True,
    secure=settings.APP_ENV == "production",
    samesite="strict",
    max_age=86400,
)
```

**Валидация:** JWT middleware ([backend/src/middleware.py](../backend/src/middleware.py)) проверяет наличие и валидность cookie.

**CSRF:** double‑submit cookie с отдельным `csrf_token`.

## 13. Решение #12: Хранение JWT-версии для отзыва токенов

### 13.1. Контекст

При смене пароля или отзыве согласия необходимо сделать все ранее выданные JWT недействительными.

### 13.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Blacklist** | Хранить список отозванных токенов в Redis. |
| **Короткий TTL** | Установить маленькое время жизни токена (например, 15 минут), использовать refresh token. |
| **Версионирование токенов (выбран)** | Добавить поле `jwt_version` в User и проверять его при каждом запросе. |

### 13.3. Обоснование

**Причины выбора версионирования:**

1. **Простота** — не требуется внешнее хранилище для blacklist.
2. **Мгновенный отзыв** — токен становится недействительным сразу после изменения версии (при следующем запросе).
3. **Интеграция с бизнес-логикой** — смена пароля, отзыв согласия — естественные точки инкремента версии.
4. **Без дополнительных сетевых вызовов** — проверка версии происходит в том же запросе к БД, что и получение пользователя.

**Компромиссы:**

- Дополнительное поле в таблице User.
- При каждом запросе выполняется запрос к БД для получения пользователя (это и так делается для аутентификации).

### 13.4. Реализация

**Модель:** [backend/src/models.py](../backend/src/models.py)

```python
class User(Base):
    # ...
    jwt_version: Mapped[int] = mapped_column(Integer, default=1)
```

**При логине:** [backend/src/services/auth_service.py](../backend/src/services/auth_service.py)

```python
async def login(self, phone, password):
    user = await self._get_user(phone)
    user.jwt_version += 1
    await self.db.flush()
    token = self._generate_token(user.id, user.jwt_version)
    return token
```

**При проверке:** в `get_current_user()`

```python
token_version = payload.get("ver", 0)
if user.jwt_version != token_version:
    raise ValueError("Token revoked")
```

**Инкремент при смене пароля:** пользовательский API смены пароля (планируется) будет увеличивать `jwt_version`.

## 14. Решение #13: CSRF double-submit cookie

### 14.1. Контекст

Использование httpOnly cookie для JWT делает систему уязвимой к CSRF-атакам. Требуется механизм защиты.

### 14.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **SameSite=Strict** | Ограничивает отправку cookie только для запросов с того же сайта. |
| **CSRF token в форме** | Генерация токена, который отправляется в теле запроса. |
| **Double-submit cookie (выбран)** | Отдельный CSRF-токен в cookie, который клиент отправляет обратно в заголовке. |
| **Заголовок Origin/Referer** | Проверка происхождения запроса. |

### 14.3. Обоснование

**Причины выбора double-submit cookie:**

1. **Простота** — не требует хранения состояния на сервере.
2. **Совместимость с SPA** — клиент может читать cookie и отправлять заголовок.
3. **Дополнительный слой** — даже при компрометации SameSite, CSRF-защита остаётся.
4. **Асинхронность** — не требует синхронной генерации токенов на каждую форму.

**Компромиссы:**

- Уязвимость, если атакующий может установить cookie на домене (но это требует более серьёзной атаки).
- Для разработки иногда удобно отключать CSRF (можно через `ENABLE_CSRF_SKIP`).

### 14.4. Реализация

**Генерация:** при логине в [backend/src/api/auth.py](../backend/src/api/auth.py)

```python
csrf_token = secrets.token_hex(32)
response.set_cookie(key="csrf_token", value=csrf_token, httponly=False, samesite="strict")
```

**Проверка:** в `verify_csrf()`

```python
cookie_value = request.cookies.get("csrf_token")
header_value = request.headers.get("X-CSRF-Token")
if not secrets.compare_digest(cookie_value, header_value):
    raise HTTPException(403, "CSRF token mismatch")
```

**Исключения:** GET-запросы и OPTIONS не проверяются. В development-режиме проверка может быть отключена через `ENABLE_CSRF=false`.

## 15. Решение #14: Шифрование PII (AES-256-GCM)

### 15.1. Контекст

Система хранит персональные данные (факты типа `personal_info`, а также любые факты с PII). В соответствии с 152-ФЗ, эти данные должны быть зашифрованы на уровне приложения.

### 15.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Шифрование на уровне БД** | Использовать встроенное шифрование PostgreSQL (TDE, pgcrypto). |
| **Шифрование на уровне приложения (выбран)** | Шифровать данные перед записью в БД с помощью AES-256-GCM. |
| **Хранение в открытом виде** | Нарушение 152-ФЗ. |
| **Использование внешнего сервиса** | HashiCorp Vault Transit, AWS KMS. |

### 15.3. Обоснование

**Причины выбора шифрования на уровне приложения:**

1. **Контроль** — мы сами управляем ключами и процессом шифрования.
2. **Гибкость** — можно шифровать только нужные поля (value фактов), а не всю БД.
3. **Безопасность** — даже при компрометации БД данные остаются зашифрованными.
4. **AES-256-GCM** — современный аутентифицированный шифр, обеспечивает целостность.

**Компромиссы:**

- Дополнительная вычислительная нагрузка на шифрование/дешифрование.
- Управление ключами (интеграция с Vault для production).

### 15.4. Реализация

**Файл:** [backend/src/utils/crypto.py](../backend/src/utils/crypto.py)

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

def encrypt(plaintext: str) -> str:
    key = _get_key()  # 32 байта из Vault / .env
    nonce = os.urandom(12)
    ciphertext = AESGCM(key).encrypt(nonce, plaintext.encode(), None)
    return base64.b64encode(nonce + ciphertext).decode()

def decrypt(ciphertext_b64: str) -> str:
    packed = base64.b64decode(ciphertext_b64)
    nonce, ciphertext = packed[:12], packed[12:]
    return AESGCM(_get_key()).decrypt(nonce, ciphertext, None).decode()
```

**Применение:** в [backend/src/services/fact_service.py](../backend/src/services/fact_service.py) при сохранении и чтении фактов.

## 16. Решение #15: Анонимизация PII через Presidio

### 16.1. Контекст

Перед сохранением фактов в память необходимо удалить из текста персональные данные (имена, адреса, телефоны, паспортные данные). Это требование 152-ФЗ.

### 16.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Регулярные выражения** | Написать набор regex для поиска PII (телефон, email, паспорт). |
| **spaCy NER** | Использовать модель распознавания именованных сущностей из spaCy. |
| **Presidio (выбран)** | Библиотека от Microsoft для обнаружения и анонимизации PII. |
| **Кастомная модель** | Обучить свою модель NER на русских данных. |

### 16.3. Обоснование

**Причины выбора Presidio:**

1. **Готовые recognizers** — телефон, email, имя, адрес, кредитные карты, IP-адреса.
2. **Расширяемость** — легко добавлять кастомные recognizers (например, для российского паспорта, СНИЛС, ИНН).
3. **Русский язык** — поддерживает русский язык (с некоторыми ограничениями, которые мы компенсируем кастомными recognizers).
4. **Активное сообщество** — от Microsoft, регулярные обновления.
5. **Простота** — API прост в использовании.

**Компромиссы:**

- Требуется установка дополнительных зависимостей (Presidio).
- Не всегда идеально распознаёт русские имена (но мы добавили кастомные recognizers).

### 16.4. Реализация

**Файлы:**
- [backend/src/utils/presidio_anonymizer.py](../backend/src/utils/presidio_anonymizer.py) — основной интерфейс.
- [backend/src/utils/presidio_russian.py](../backend/src/utils/presidio_russian.py) — кастомные recognizers для российских документов.

```python
def anonymize_text(text: str) -> str:
    analyzer = _get_analyzer()   # с кастомными recognizers
    anonymizer = _get_anonymizer()
    results = analyzer.analyze(text=text, language="ru")
    return anonymizer.anonymize(text=text, analyzer_results=results).text
```

**Применение:** в `FactExtractorAgent._extract_triplets` перед сохранением.

## 17. Решение #16: Право на забвение (RTBF) каскадное удаление

### 17.1. Контекст

152-ФЗ требует, чтобы пользователь мог полностью удалить свои данные по запросу, и это должно быть выполнено в течение 24 часов.

### 17.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Мягкое удаление** | Помечать данные как удалённые, но физически не удалять. |
| **Анонимизация** | Заменить PII на placeholder, но оставить факты. |
| **Каскадное удаление (выбран)** | Физически удалить все данные из всех хранилищ. |

### 17.3. Обоснование

**Причины выбора каскадного удаления:**

1. **Соответствие 152-ФЗ** — закон требует именно удаления, а не пометки.
2. **Прозрачность** — пользователь уверен, что его данные удалены.
3. **Простота** — удаление проще, чем поддержка логики «мягкого удаления».

**Компромиссы:**

- Удаление необратимо (требуется подтверждение от пользователя).
- Восстановление невозможно без бэкапов (но бэкапы делаются).

### 17.4. Реализация

**Файл:** [backend/src/services/right_to_be_forgotten_service.py](../backend/src/services/right_to_be_forgotten_service.py)

```python
async def delete_user_data(self, user_id: UUID) -> dict:
    # 1. PostgreSQL: удалить факты, сессии, consent, user
    await self._delete_from_postgres(user_id)
    # 2. Qdrant: удалить все точки
    await self._delete_from_qdrant(user_id)
    # 3. Neo4j: удалить все узлы
    await self._delete_from_neo4j(user_id)
    # 4. MinIO: удалить все файлы
    await self._delete_from_minio(user_id)
    return {"status": "deleted", ...}
```

**Триггеры:** API `/consents/revoke` и `/consents/data-deletion`.

## 18. Решение #17: Аудит всех операций с памятью

### 18.1. Контекст

152-ФЗ требует ведения аудита всех действий с персональными данными: кто, когда, что делал.

### 18.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **Только логи** | Писать логи в файл, но не структурированно. |
| **Структурированная таблица аудита (выбран)** | Таблица `AuditLog` в PostgreSQL с полями user_id, action, timestamp, source. |
| **Внешняя система аудита** | Отправлять события в Elasticsearch или аналоги. |

### 18.3. Обоснование

**Причины выбора таблицы аудита:**

1. **Структурированность** — легко делать запросы, фильтровать, анализировать.
2. **Требования 152-ФЗ** — аудит должен храниться 3 года, таблица обеспечивает это.
3. **Интеграция с приложением** — запись аудита происходит в том же транзакционном контексте, что и операция.
4. **Простота** — не требует внешних систем.

**Компромиссы:**

- Дополнительная нагрузка на БД (но это оправдано требованиями).
- Хранение 3 лет требует планирования размера таблицы (но данных не слишком много).

### 18.4. Реализация

**Модель:** [backend/src/models.py](../backend/src/models.py)

```python
class AuditLog(Base):
    id: UUID
    user_id: UUID
    action: str  # READ, WRITE, DELETE
    fact_id: UUID | None
    timestamp: datetime
    source: str  # AI, OPERATOR
    ip_address: str | None
```

**Запись:** через [backend/src/services/audit_service.py](../backend/src/services/audit_service.py).

```python
async def log_action(self, user_id, action, fact_id=None, source="AI", ip_address=None):
    audit = AuditLog(...)
    self.db.add(audit)
    await self.db.flush()
```

**Вызов:** во всех методах `FactService` (store, get, delete, search) и в `ConsentService`.

## 19. Решение #18: Миграции через Alembic

### 19.1. Контекст

Управление схемой БД должно быть контролируемым, версионированным и безопасным для production.

### 19.2. Альтернативы

| Подход | Описание |
|--------|----------|
| **create_all() при старте** | Автоматически создавать таблицы из моделей (было изначально). |
| **Alembic (выбран)** | Инструмент для миграций с автоматической генерацией и версионированием. |
| **Ручные SQL-скрипты** | Вручную писать ALTER TABLE и применять. |

### 19.3. Обоснование

**Причины выбора Alembic:**

1. **Версионирование** — каждая миграция имеет номер, можно отслеживать изменения.
2. **Автоматическая генерация** — `alembic revision --autogenerate` создаёт миграцию на основе изменений моделей.
3. **Безопасность** — можно откатить миграцию (`alembic downgrade`).
4. **Производственная зрелость** — стандарт для SQLAlchemy.

**Компромиссы:**

- Требуется настройка (async env.py).
- Миграции нужно проверять вручную перед применением в production (особенно если есть необратимые изменения).

### 19.4. Реализация

**Инициализация:** `alembic init -t async alembic`

**Файлы:**
- [backend/alembic.ini](../backend/alembic.ini)
- [backend/alembic/env.py](../backend/alembic/env.py) — асинхронная настройка.
- [backend/alembic/versions/](../backend/alembic/versions/) — две миграции: `001_initial_schema.py` и `002_remove_encrypted_data.py`.

**В `main.py`** удалён вызов `init_db()` — теперь таблицы создаются только через Alembic.
