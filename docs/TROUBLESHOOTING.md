# 🔧 TROUBLESHOOTING.md

## 1. Введение

### 1.1. Цель документа

Данное руководство содержит описание наиболее частых проблем, возникающих при работе с системой «Омниканальный агент с долговременной памятью», и шаги по их устранению. Оно предназначено для операторов, разработчиков и администраторов, которые сталкиваются с ошибками в процессе эксплуатации и отладки системы.

Для каждой проблемы указаны возможные причины, диагностические шаги и конкретные действия по исправлению. Если предложенные решения не помогают, рекомендуется обратиться к команде разработки или воспользоваться [RUNBOOK.md](RUNBOOK.md) для более глубокого анализа.

### 1.2. Структура раздела

Каждая проблема описывается по следующему шаблону:

- **Симптомы** — что вы видите (сообщение об ошибке, поведение системы).
- **Возможные причины** — что могло вызвать проблему.
- **Диагностика** — команды для проверки состояния.
- **Решение** — шаги по устранению.
- **Предотвращение** — как избежать проблемы в будущем.

## 2. Проблемы аутентификации и авторизации

### 2.1. Ошибка 401 Unauthorized

**Симптомы:**
- При попытке доступа к защищённому эндпоинту возвращается `401 Unauthorized`.
- В браузере отсутствует cookie `access_token`.

**Возможные причины:**
- Пользователь не авторизован (не выполнен вход).
- Срок действия JWT истёк (24 часа по умолчанию).
- JWT был отозван (смена пароля, отзыв согласия).
- Cookie не передаётся из-за неправильных настроек CORS или SameSite.

**Диагностика:**
```bash
# Проверить наличие cookie в браузере (инструменты разработчика → Application → Cookies)
# Или через curl:
curl -v https://app.example.com/auth/me
```

**Решение:**
1. Выполните повторный вход через `/auth/login`.
2. Если ошибка сохраняется, проверьте, что `JWT_SECRET` совпадает с тем, который использовался при создании токена (если менялся — все токены становятся недействительными).
3. Проверьте, что cookie имеет правильные атрибуты (`Secure` для HTTPS, `SameSite`).
4. В development-режиме убедитесь, что `APP_ENV=development` и cookie не требует HTTPS.

**Предотвращение:**
- Настройте автоматическое обновление токена (refresh token) — планируется.
- Информируйте пользователей о сроке действия сессии.

### 2.2. Ошибка 403 Forbidden

**Симптомы:**
- Доступ к ресурсу запрещён, возвращается `403 Forbidden`.
- В логах: `Admin access required` или `CSRF token mismatch`.

**Возможные причины:**
- Недостаточно прав (например, попытка доступа к административному эндпоинту без роли `admin`).
- CSRF-токен отсутствует или не совпадает.
- Нет активного согласия на обработку данных (152-ФЗ).

**Диагностика:**
```bash
# Проверить роль пользователя
curl -X GET https://app.example.com/auth/me -b cookies.txt

# Проверить CSRF-токен
# Убедиться, что в заголовках запроса есть X-CSRF-Token
```

**Решение:**
1. Для административных эндпоинтов убедитесь, что у пользователя роль `admin` (проверить в БД или через `/auth/me`).
2. Для CSRF:
   - Убедитесь, что в запросе присутствует заголовок `X-CSRF-Token` со значением из cookie `csrf_token`.
   - В development-режиме CSRF может быть отключён (`ENABLE_CSRF=false`).
3. Для согласия: проверьте статус через `/consents/status`. Если согласие отсутствует, запросите его через `/consents/grant`.

**Предотвращение:**
- Используйте ролевую модель правильно (не давайте лишних прав).
- Включайте CSRF-защиту в production (по умолчанию включена).

### 2.3. Ошибка 429 Too Many Requests

**Симптомы:**
- Сервер возвращает `429 Too Many Requests` с заголовком `Retry-After`.
- Часто возникает при частых попытках входа или отправке большого количества запросов.

**Возможные причины:**
- Превышен лимит запросов (rate limiting).
- Активная защита от брутфорса (при множественных неудачных попытках входа).

**Диагностика:**
```bash
# Проверить заголовки ответа
curl -v https://app.example.com/auth/login -X POST -d '{"phone":"...","password":"..."}'
```

**Решение:**
1. Подождите указанное в `Retry-After` время (обычно 60 секунд для rate limiting, 5 минут для брутфорса).
2. Для брутфорса: если вы уверены в правильности данных, проверьте, не заблокирован ли пользователь (см. логи).
3. Для администраторов: при необходимости временно отключите rate limiting (только для отладки).

**Предотвращение:**
- Используйте корректные учётные данные.
- Не отправляйте слишком много запросов за короткое время.
- Для брутфорса: реализуйте механизм блокировки только после 5 неудачных попыток (планируется).

## 3. Проблемы с памятью и фактами

### 3.1. Агент не запоминает факты

**Симптомы:**
- После отправки сообщения агент не использует память в последующих ответах.
- В логах нет записей о сохранении фактов.

**Возможные причины:**
- `ENABLE_MEMORY=false` (Feature Flag отключён).
- `ENABLE_LLM=false` (LLM отключена, факты не извлекаются).
- Нет активного согласия пользователя (`Consent`).
- Celery не обрабатывает задачи (воркеры не запущены или очередь заблокирована).

**Диагностика:**
```bash
# Проверить статус Feature Flags
curl https://app.example.com/chat/health
curl https://app.example.com/voice/health

# Проверить статус согласия
curl https://app.example.com/consents/status -b cookies.txt

# Проверить Celery
kubectl logs -n omnichannel deployment/celery-worker --tail=50
```

**Решение:**
1. Убедитесь, что `ENABLE_MEMORY=true` и `ENABLE_LLM=true` в `.env` / ConfigMap.
2. Проверьте, что у пользователя есть активное согласие (если нет — запросите через интерфейс).
3. Перезапустите Celery воркеры: `kubectl rollout restart deployment/celery-worker -n omnichannel`.
4. Проверьте очередь Redis: `redis-cli LLEN celery` — если длина растёт, значит, воркеры не справляются.

**Предотвращение:**
- Включите мониторинг очереди Celery.
- Убедитесь, что Feature Flags настроены правильно для production.

---

### 3.2. Поиск памяти возвращает нерелевантные результаты

**Симптомы:**
- Агент находит факты, которые не имеют отношения к вопросу.
- Поиск не находит очевидно релевантные факты.

**Возможные причины:**
- Неправильная настройка эмбеддингов (например, модель не подходит для русского языка).
- Маленький вес фактов (ниже порога 0.3 не участвуют в поиске).
- Ошибки в Qdrant (индексы повреждены, коллекция не создана).

**Диагностика:**
```bash
# Проверить эмбеддинги в логах (поиск по "embedding")
kubectl logs -n omnichannel deployment/backend --tail=100 | grep embedding

# Проверить Qdrant
curl -s http://qdrant:6333/collections/omnichannel | jq .
```

**Решение:**
1. Убедитесь, что используется правильная модель эмбеддингов (`EMBEDDING_MODEL=paraphrase-multilingual-MiniLM-L12-v2`).
2. Проверьте, что факты имеют достаточный вес (если < 0.3 — они не участвуют в поиске). Можно вручную увеличить вес через API.
3. Переиндексируйте факты в Qdrant (если коллекция повреждена, удалите и создайте заново).

**Предотвращение:**
- Регулярно проверяйте качество эмбеддингов.
- Настройте мониторинг количества фактов и их весов.

---

### 3.3. Ошибка "Consent required" при чтении фактов

**Симптомы:**
- При запросе фактов возвращается `403 Forbidden` с сообщением о необходимости согласия.

**Возможные причины:**
- Пользователь отозвал согласие.
- Согласие истекло (если настроен срок действия).

**Диагностика:**
```bash
curl https://app.example.com/consents/status -b cookies.txt
```

**Решение:**
1. Попросите пользователя заново выдать согласие через `/consents/grant`.
2. Если согласие было отозвано, данные уже удалены (RTBF). Восстановление невозможно.

**Предотвращение:**
- Информируйте пользователей о необходимости согласия перед использованием памяти.
- Реализуйте механизм повторного запроса согласия при истечении срока.

## 4. Проблемы с голосовым пайплайном

### 4.1. ASR не распознаёт речь (пустой или бессмысленный текст)

**Симптомы:**
- `POST /voice/transcribe` возвращает пустой `text` или текст с ошибками.
- В логах ошибки `WhisperASR` или `speechkit`.

**Возможные причины:**
- `ENABLE_ASR=false` или `ENABLE_VOICE=false`.
- Whisper модель не загружена (ленивая инициализация не сработала).
- Аудиофайл имеет неподдерживаемый формат или низкое качество.
- Проблемы с GPU (если используется).

**Диагностика:**
```bash
# Проверить статус голосовых сервисов
curl https://app.example.com/voice/health

# Проверить логи ASR
kubectl logs -n omnichannel deployment/backend | grep -i whisper
```

**Решение:**
1. Убедитесь, что `ENABLE_ASR=true` и `ENABLE_VOICE=true`.
2. Проверьте формат аудио (поддерживаются WAV, MP3, WebM, OGG, не более 10 МБ).
3. Перезапустите backend (для перезагрузки модели ASR).
4. Если используется GPU, проверьте наличие драйверов и доступ к GPU.

**Предотвращение:**
- Добавьте валидацию аудиофайлов (размер, формат) — планируется.
- Настройте мониторинг использования GPU.

### 4.2. TTS генерирует артефактный или обрезанный звук

**Симптомы:**
- Синтезированная речь содержит щелчки, шумы или обрывается.
- Длительность аудио не соответствует тексту.

**Возможные причины:**
- `ENABLE_TTS=false` или `ENABLE_VOICE=false`.
- Silero модель повреждена или не загружена.
- Некорректный текст (слишком длинный, содержит специальные символы).

**Диагностика:**
```bash
# Проверить логи TTS
kubectl logs -n omnichannel deployment/backend | grep -i silero
```

**Решение:**
1. Убедитесь, что `ENABLE_TTS=true`.
2. Проверьте, что текст не превышает 1000 символов (рекомендуемый лимит).
3. Перезапустите backend для перезагрузки Silero модели.
4. Если проблема сохраняется, попробуйте использовать другой голос (параметр `voice`).

**Предотвращение:**
- Ограничьте длину текста для TTS.
- Настройте мониторинг ошибок TTS.

---

### 4.3. WebSocket `/voice/stream` закрывается с ошибкой

**Симптомы:**
- Подключение к WebSocket разрывается сразу после установки.
- В логах ошибка `Voice processing disabled`.

**Возможные причины:**
- `ENABLE_VOICE=false`.
- Неправильный формат аудиопотока.
- Превышение лимитов (например, слишком большой чанк).

**Диагностика:**
```bash
# Проверить логи WebSocket
kubectl logs -n omnichannel deployment/backend | grep -i websocket
```

**Решение:**
1. Убедитесь, что `ENABLE_VOICE=true`.
2. Проверьте формат аудио (ожидается PCM или Opus).
3. Уменьшите размер аудиочанков (рекомендуется 20–40 мс).
4. Перезапустите backend.

**Предотвращение:**
- Добавьте валидацию аудиопотока перед обработкой.
- Настройте таймауты WebSocket.

## 5. Проблемы с интеграциями и вебхуками

### 5.1. Вебхук Telegram не принимается (403 Forbidden)

**Симптомы:**
- Telegram не отправляет сообщения в систему или возвращает ошибку.
- В логах: `Telegram webhook rejected: invalid secret token`.

**Возможные причины:**
- Неправильно задан `TELEGRAM_WEBHOOK_SECRET` в `.env` / ConfigMap.
- Telegram не передаёт заголовок `X-Telegram-Bot-Api-Secret-Token`.

**Диагностика:**
```bash
# Проверить логи вебхуков
kubectl logs -n omnichannel deployment/backend | grep -i telegram
```

**Решение:**
1. Убедитесь, что `TELEGRAM_WEBHOOK_SECRET` совпадает с тем, что установлен в настройках бота (через `setWebhook`).
2. Проверьте, что в запросе присутствует заголовок `X-Telegram-Bot-Api-Secret-Token`.
3. Если секрет не настроен, отключите проверку (установите пустую строку в development-режиме).

**Предотвращение:**
- Храните секрет в Vault / K8s Secrets.
- Настройте автоматическую проверку вебхуков.

---

### 5.2. Вебхук VK не проходит подтверждение

**Симптомы:**
- VK не может подтвердить сервер (ошибка при настройке Callback API).
- В логах: `VK webhook rejected: invalid secret`.

**Возможные причины:**
- Неправильно задан `VK_CALLBACK_SECRET`.
- Отсутствует параметр `secret` в callback-запросе.

**Диагностика:**
```bash
# Проверить логи VK
kubectl logs -n omnichannel deployment/backend | grep -i vk
```

**Решение:**
1. Убедитесь, что `VK_CALLBACK_SECRET` совпадает с тем, что указан в настройках группы VK.
2. Проверьте, что в запросе присутствует поле `secret`.
3. Для подтверждения (`confirmation`) проверка пропускается — убедитесь, что эндпоинт возвращает `VK_GROUP_ID`.

**Предотвращение:**
- Храните секрет в защищённом месте.
- Тестируйте вебхуки перед развёртыванием в production.

## 6. Проблемы с производительностью

### 6.1. Медленные ответы (высокая задержка API)

**Симптомы:**
- Запросы выполняются дольше обычного (более 3 секунд).
- Пользователи жалуются на долгие ответы.

**Возможные причины:**
- Высокая нагрузка на LLM (квоты API, медленный инференс).
- Большая очередь Celery (задачи накапливаются).
- Проблемы с БД (медленные запросы, нехватка ресурсов).

**Диагностика:**
```bash
# Проверить задержки через Prometheus
# Или через логи:
kubectl logs -n omnichannel deployment/backend --tail=100 | grep duration

# Проверить очередь Celery
kubectl exec -it deployment/redis -n omnichannel -- redis-cli LLEN celery
```

**Решение:**
1. Проверьте метрики LLM (Grafana). Если задержка > 5с, рассмотрите смену провайдера или увеличение квот.
2. Увеличьте количество Celery воркеров (см. [SCALING_GUIDE.md](SCALING_GUIDE.md)).
3. Проверьте БД: выполните `ANALYZE` для таблиц, оптимизируйте запросы.
4. Увеличьте ресурсы (CPU/Memory) для компонентов.

**Предотвращение:**
- Настройте HPA для автоматического масштабирования.
- Оптимизируйте индексы в PostgreSQL, Qdrant, Neo4j.

### 6.2. Высокое использование памяти (OOM)

**Симптомы:**
- Поды перезапускаются с ошибкой OOMKilled.
- В логах ошибки выделения памяти.

**Возможные причины:**
- Модели (Whisper, Silero, Cross-Encoder) требуют много памяти.
- Утечка памяти (например, не освобождаются ресурсы после обработки).

**Диагностика:**
```bash
# Проверить использование памяти
kubectl top pods -n omnichannel

# Посмотреть события OOM
kubectl describe pod -n omnichannel <pod-name>
```

**Решение:**
1. Увеличьте лимиты памяти в Deployment.
2. Для моделей с большим потреблением памяти используйте отдельные поды с большими ресурсами.
3. Проверьте, что модели правильно выгружаются из памяти (особенно при `ENABLE_LLM=false`).

**Предотвращение:**
- Мониторьте использование памяти в Grafana.
- Настройте алерты на превышение 80% памяти.

## 7. Проблемы с миграциями и схемой БД

### 7.1. Ошибка "Table 'facts' already exists" при `alembic upgrade head`

**Симптомы:**
- Миграция не применяется из-за существующих таблиц.

**Возможные причины:**
- Ранее использовался `create_all()` (устаревший подход).
- БД содержит таблицы, но версия Alembic не соответствует.

**Диагностика:**
```bash
# Проверить версию Alembic
alembic current
```

**Решение:**
1. Если таблицы уже существуют, но миграции не применялись, можно создать начальную миграцию вручную (`alembic stamp head` для маркировки текущего состояния).
2. В противном случае удалите таблицы и примените миграции заново (осторожно!).

**Предотвращение:**
- Используйте только Alembic для управления схемой.
- Убедитесь, что `init_db()` удалён из `main.py`.
