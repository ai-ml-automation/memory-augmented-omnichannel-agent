# 📖 OPERATOR_GUIDE.md

## 1. Введение

Данное руководство предназначено для операторов службы поддержки и администраторов системы «Омниканальный агент с долговременной памятью». В нём описаны все необходимые действия по управлению памятью клиентов, обработке запросов на удаление данных, аудиту и настройке системы.

Операторы имеют доступ к веб-интерфейсу, который позволяет просматривать и управлять памятью клиентов, а также выполнять административные функции.

**Ключевые возможности:**
- Просмотр и управление фактами памяти клиентов.
- Удаление отдельных фактов или всех данных клиента (право на забвение).
- Просмотр аудит-лога всех действий с памятью.
- Управление согласием на обработку данных (152-ФЗ).
- Управление привязками каналов (для администраторов).

## 2. Просмотр памяти клиента

### 2.1. Через фронтенд

Перейдите на страницу **«Память»** (доступна по ссылке `/memory/:userId` в боковом меню или через прямой переход).

1. В поле ввода введите **идентификатор пользователя** (UUID) и нажмите «Загрузить факты».
2. Отобразится таблица всех фактов пользователя с колонками:
   - **Тип** (intent, preference, complaint, agreement, rejection, personal_info) — отображается цветным бейджем.
   - **Значение** — текст факта (анонимизирован при необходимости).
   - **Вес** — важность факта (от 0 до 1).
   - **Канал** — источник (MAX, TG, VK, VOICE, WEB).
   - **Дата** — время создания.
   - **Статус** — активен, заменён, истёк.

3. Для поиска конкретных фактов используйте строку поиска и фильтр по типу факта. Также доступен режим «Граф связей» (заглушка, показывающая связи между фактами).

![Просмотр памяти клиента](images/memory.png)

*Скриншот: страница «Память» с таблицей фактов пользователя.*

### 2.2. Через API

```bash
# Получить все факты пользователя
curl -X GET "http://localhost:8000/api/v1/memory/users/{user_id}/facts?limit=100" \
  -H "Cookie: access_token=<your-token>"

# Поиск по памяти (гибридный поиск)
curl -X POST "http://localhost:8000/api/v1/memory/users/{user_id}/search" \
  -H "Cookie: access_token=<your-token>" \
  -H "Content-Type: application/json" \
  -d '{"query": "безлимит", "search_type": "hybrid", "limit": 5}'
```

Подробное описание эндпоинтов см. в [API_REFERENCE.md](API_REFERENCE.md).

## 3. Удаление конкретного факта

### 3.1. Через фронтенд

На странице памяти клиента:

1. Найдите нужный факт в таблице.
2. Нажмите на иконку корзины (или кнопку «Удалить»).
3. Подтвердите удаление во всплывающем диалоге.
4. Факт будет удалён из PostgreSQL, Qdrant и Neo4j.

> **Важно:** Удаление необратимо. Факт удаляется из всех хранилищ.

![Удаление факта из памяти](images/memory.png)

*Скриншот: кнопка удаления факта на странице «Память».*

### 3.2. Через API

```bash
curl -X DELETE "http://localhost:8000/api/v1/memory/users/{user_id}/facts/{fact_id}" \
  -H "Cookie: access_token=<your-token>"
```

**Коды ответа:**
- `200 OK` — успешно удалено.
- `404 Not Found` — факт не найден или не принадлежит пользователю.
- `403 Forbidden` — нет активного согласия или недостаточно прав.

## 4. Полное удаление данных (RTBF) — 152-ФЗ

**Право на забвение (Right to be Forgotten)** — полное каскадное удаление всех данных клиента по его запросу или по инициативе оператора.

### 4.1. Через фронтенд (для пользователя)

Страница **«Право на забвение»** (доступна по ссылке `/forget` в боковом меню).

1. На странице отображается информация о том, какие данные будут удалены.
2. Введите слово **«УДАЛИТЬ»** в поле подтверждения (латиницей или кириллицей, как указано на странице).
3. Нажмите кнопку «Удалить мои данные».
4. Система выполнит каскадное удаление:
   - **PostgreSQL:** удаляет все факты, сессии, привязки каналов, согласие (revoked) и запись пользователя.
   - **Qdrant:** удаляет все векторные точки с `user_id`.
   - **Neo4j:** удаляет все узлы и рёбра, связанные с пользователем.
   - **MinIO:** удаляет все аудиофайлы пользователя.
5. После завершения пользователь будет автоматически разлогинен и перенаправлен на страницу входа.

![Право на забвение (RTBF)](images/forget.png)

*Скриншот: страница «Право на забвение» с полем подтверждения.*

### 4.2. Через API

```bash
# Выполнить RTBF (эквивалентно revoke consent)
curl -X POST "http://localhost:8000/api/v1/consents/data-deletion" \
  -H "Cookie: access_token=<your-token>"
```

**Ответ:**
```json
{
  "status": "deleted",
  "postgres_facts_deleted": 15,
  "qdrant_facts_deleted": 15,
  "neo4j_facts_deleted": 15,
  "user_deleted": true
}
```

> **Важно:** RTBF также автоматически срабатывает при отзыве согласия (`POST /consents/revoke`).

## 5. Аудит-лог

Все действия с памятью (чтение, запись, удаление) логируются в таблицу `AuditLog` для соответствия 152-ФЗ.

### 5.1. Через фронтенд

Страница **«Аудит»** (доступна по ссылке `/audit` в боковом меню).

1. Отображается таблица с записями аудита:
   - **Время** — когда произошло действие.
   - **Действие** (READ, WRITE, DELETE) — цветной бейдж.
   - **User ID** — идентификатор пользователя, чьи данные затронуты.
   - **Источник** (AI или OPERATOR).
   - **Fact ID** — идентификатор факта (если применимо).
   - **IP-адрес** — с которого был выполнен запрос.
2. Доступны фильтры:
   - По User ID.
   - По типу действия.
   - По источнику.
   - По диапазону дат.
3. Пагинация позволяет просматривать длинные списки.

![Аудит-лог](images/audit_log.png)

*Скриншот: страница «Аудит» с фильтрами и таблицей записей.*

### 5.2. Через API

Аналитические эндпоинты позволяют получить агрегированные данные аудита:

```bash
# Таймлайн аудита (количество событий по дням)
curl "http://localhost:8000/api/v1/analytics/audit/timeline?days=7" \
  -H "Cookie: access_token=<your-token>"

# Часы пиковой активности
curl "http://localhost:8000/api/v1/analytics/audit/peak-hours" \
  -H "Cookie: access_token=<your-token>"
```

Для получения полного списка записей с фильтрацией необходимо использовать прямой доступ к БД (для администраторов) или дождаться реализации соответствующего эндпоинта.

## 6. Управление согласием (152-ФЗ)

### 6.1. Через фронтенд

Страница **«Профиль»** (доступна по ссылке `/profile` в боковом меню).

1. В разделе «Согласие на обработку персональных данных» отображается текущий статус.
2. Кнопка **«Выдать согласие»** — сохраняет согласие в таблице `Consent`.
3. Кнопка **«Отозвать согласие»** — отзывает согласие и **автоматически запускает RTBF** (каскадное удаление всех данных).

![Профиль: согласие на обработку данных](images/profile_top.png)

*Скриншот: раздел «Согласие на обработку персональных данных» на странице «Профиль».*

### 6.2. Через API

```bash
# Проверить статус согласия
curl -X GET "http://localhost:8000/api/v1/consents/status" \
  -H "Cookie: access_token=<your-token>"

# Выдать согласие
curl -X POST "http://localhost:8000/api/v1/consents/grant" \
  -H "Cookie: access_token=<your-token>" \
  -H "Content-Type: application/json" \
  -d '{"channel": "WEB", "ip_address": "192.168.1.1"}'

# Отозвать согласие (триггерит RTBF)
curl -X POST "http://localhost:8000/api/v1/consents/revoke" \
  -H "Cookie: access_token=<your-token>"
```

## 7. Управление каналами (для администраторов)

Администраторы могут управлять привязками пользователей к внешним каналам (MAX, Telegram, VK, Voice). Это полезно для исправления ошибок или ручной привязки.

### 7.1. Через фронтенд

Страница **«Каналы»** (доступна по ссылке `/operator/channels` в боковом меню).

1. Отображается таблица всех привязок с колонками:
   - **Канал** (MAX, TG, VK, VOICE).
   - **User ID** — внутренний идентификатор пользователя.
   - **External ID** — внешний идентификатор в канале.
   - **Статус** (активен/неактивен).
2. Кнопка **«Отвязать»** для удаления привязки (soft delete, помечает как неактивную).

![Управление каналами (оператор)](images/operator_channels.png)

*Скриншот: страница «Каналы» с таблицей привязок.*

### 7.2. Через API

```bash
# Получить список всех привязок
curl -X GET "http://localhost:8000/api/v1/admin/channels" \
  -H "Cookie: access_token=<your-token>"

# Создать привязку
curl -X POST "http://localhost:8000/api/v1/admin/channels" \
  -H "Cookie: access_token=<your-token>" \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user-uuid", "channel_type": "TG", "external_id": "123456789"}'

# Удалить привязку
curl -X DELETE "http://localhost:8000/api/v1/admin/channels/{binding_id}" \
  -H "Cookie: access_token=<your-token>"
```

## 8. Memory Decay (автоматическое устаревание фактов)

Система автоматически уменьшает вес фактов со временем, чтобы старые факты переставали влиять на ответы агента.

### 8.1. Как это работает

- **Цикл decay:** раз в час (запускается Celery Beat).
- **Множитель:** вес умножается на 0.99 за цикл (≈ 1% в день).
- **Мягкое удаление:** если вес становится < 0.1, факт помечается как `superseded` и перестаёт участвовать в поиске.
- **Жёсткое удаление:** если `expires_at` истекло, факт удаляется полностью (hard delete).

### 8.2. Настройка через переменные окружения

| Переменная | Описание | Значение по умолчанию |
|------------|----------|------------------------|
| `DECAY_INTERVAL_HOURS` | Интервал запуска decay (часы) | 1 (через Celery Beat) |
| `MIN_WEIGHT` | Минимальный вес для участия в поиске | 0.1 |
| `DECAY_MULTIPLIER` | Множитель убывания | 0.99 |
| `DEFAULT_TTL_DAYS` | Срок жизни факта (дни) | 90 |

### 8.3. Мониторинг

Операторы могут отслеживать количество удалённых фактов через дашборд Grafana (панель «Facts Expired») или через логи (поиск по `DecayAgent`).

## 9. Часто задаваемые вопросы

**Q: Могу ли я восстановить удалённый факт?**  
A: Нет, удаление необратимо. Используйте бэкапы для восстановления (требуется вмешательство администратора).

**Q: Что происходит с памятью при деактивации пользователя?**  
A: Пользователь деактивируется (устанавливается `is_active = false`), но факты остаются в БД. При повторной активации память восстанавливается.

**Q: Как часто извлекаются новые факты?**  
A: При каждом сообщении пользователя (если включён `ENABLE_LLM=true`). Извлечение происходит асинхронно через Celery и не блокирует ответ.

**Q: Память работает без LLM?**  
A: Без LLM работает поиск и хранение, но извлечение новых фактов не происходит. Агент будет использовать только существующие факты.

**Q: Как проверить, что RTBF выполнен?**  
A: Проверьте аудит-лог на наличие события с действием `DELETE` и статусом `completed`, а также убедитесь, что при повторном запросе `/memory/users/{id}/facts` возвращается пустой список (или ошибка 404, если пользователь удалён).

**Q: Как отключить память для конкретного канала?**  
A: Отзовите согласие для канала через API или UI. Это автоматически удалит все данные этого пользователя (RTBF).
